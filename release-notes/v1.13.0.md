## v1.13.0 — 游戏设备优先通道（设备级 QoS）

### 版本特色

给一台设备（游戏主机/PC）开专属优先通道：它的全部流量在双向 cake 整形中进入高优先 video 桶。设计对标华硕「游戏加速 LAN 口」/ DUMAOS 设备级优先——但我们把机制做透明：页面上直接显示双向分桶速率（真实 tc 计数器），开了就有 Video 行，效果可自行验证，不黑箱。

### 新增

- **游戏通道 Tab**：设备 IP 一键开启；五态徽标诚实降级（未开启 / 优先中 / 有残留规则 / 标记缺失 / SQM 未运行·直通 / 整形未切换）
- **出口延迟曲线**：每 8s 采样，滚动 5 分钟 sparkline
- **双向分桶表**：上行/下行各 tin 的速率、包数、丢包（来自 `tc -s` 实时计数）
- **netsteer-qos**：nftables 双向 DSCP CS4 标记（forward 出向改写 + ingress 钩子入向改写）；`netsteer-gaming.qos` 切 cake diffserv4 + 上行 ack-filter；幂等 reapply，init.d/hotplug 双挂自愈，关闭自动还原 simple.qos

### 实测（NanoPi R5C · OpenWrt 25.12.6 · 电信 1000M/50M PPPoE · cake 900M/48M）

- **机制验证**：开启后被标记设备的包确实落入 video 桶——内核计数器实测（30M 整形窗口）：下行 video tin +8053 pkts、上行 +300 pkts
- **带宽份额（通道的核心价值）**：30M 整形被 8 条 bulk 流打满（负载 100%）时，被标记路径的吞吐 OFF 0.23 Mbps → ON 0.58 Mbps，**2.47×**（4 轮全部同向；方法论：ICPM flood 探测流，小流量，方向性结论）
- **延迟（如实标注）**：100% 饱和下被标记路径 ping OFF 5.44ms vs ON 6.10ms（3+3 轮）——cake 的流隔离在两个状态下都把满载延迟压在 ~6ms（对比无 SQM 满载 58.6ms），四桶调度有 +0.7ms 开销。**通道的增益在带宽份额与确定性隔离，不在延迟**（延迟保护是 cake 本身的功劳）
- **质量门**：单测 177 项全绿（v1.12 基线 138）；4 架构（aarch64_generic / aarch64_cortex-a53 / x86_64 / mipsel_24kc）apk verify 全过；真机 e2e 12 项 ALL GREEN（含 UI 开关往返）；真机装卸循环验证（卸载自动还原 simple.qos，重装状态无损）

### 修复

- rpcd ACL 缺 `/usr/bin/netsteer-qos` exec 白名单 → UI 调用 403（已修 + 新增防回归单测：ACL 与 fs.exec 一致性校验）
- busybox ping 不支持小数 `-i` → probe 采样静默零回包（改 `-i 1`）
- e2e 三处过时断言修正（data-sec 卡片选择器、问号按钮在专家调教面板、移动端 context 未登录假阳性）

### 已知边界（页面内亦有注明）

- 仅 IPv4 流量标记（游戏主机/PC 绝大多数流量走 v4）
- 需 SQM cake 运行（均衡/低延迟/P2P 模式）；极速模式或总开关关闭时通道自动降级并如实显示
- 被标记设备上的 Steam 大文件下载同样走优先桶——cake 流隔离保证游戏包延迟不受其排队影响，带宽按流公平分享
